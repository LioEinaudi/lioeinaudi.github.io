*一个双卡测量项目如何变成我第一个合入 vLLM 的 PR（[#53247](https://github.com/vllm-project/vllm/pull/53247)），以及它教给我的测量纪律。*

## 为什么需要 batch invariance

在任意一个现代推理引擎里，拿同一个问题问两次 LLM——哪怕用贪心采样、temperature 设为 0——你依然可能拿到两份不同的回答。问题不出在采样，而在于你这次请求跟谁凑进了同一个 batch。随着 batch 组成变化，kernel 内部的规约顺序会跟着变，而浮点加法不满足结合律，logprob 就会漂移几个 ULP。平时大多无所谓，但如果你在做 RL rollout 需要逐位精确复现，或者在排查训练与推理的数值偏差，这种不确定性就很致命。

vLLM 提供了 batch-invariant 模式（`VLLM_BATCH_INVARIANT=1`），会把受 batch 影响的算子替换成批不变版本。代价是慢。社区管这部分额外开销叫 **determinism tax（确定性税）**；我刚上手测的时候，在我的硬件上，吞吐直接掉 30%–35%。

这篇文章记录的是怎么把这笔税具体花在哪给查出来，并把最大的一块给调掉。最终改动合入上游成了 [PR #53247](https://github.com/vllm-project/vllm/pull/53247)：**H20 上 batch 8 端到端延迟降低 29.4%（1.42×）、吞吐提升 3.4%**，**RTX 4090D 上 batch 8 延迟降低 23.0%、吞吐提升 12.0%**，同时逐位不变性完好无损。

## 实验环境：两张大厂不太会专门调优的卡

我特意租了两类不在 H100/B200 主流视野里的云卡：

- **NVIDIA H20** —— 96 GB，Hopper（sm90），显存带宽极大但算力只有 H100 的约 1/6，国内生产环境的主力推理卡。
- **RTX 4090D** —— 24 GB，Ada（sm89），消费级芯片，没有 TMA，也没有 WGMMA。

测试模型选 Qwen3-1.7B，配两套脚本：

1. **开销基准（tax benchmark）**：分别测 `VLLM_BATCH_INVARIANT` 开/关、编译模式与 eager 模式下的服务吞吐和延迟。
2. **不变性探针（invariance probe）**：把一条“探针” prompt 先单独跑一遍，再混进 batch=32 里跑一遍（贪心采样、关闭 prefix cache），在 **fp32 下逐位比对 logprob**。调优过的 kernel 只有探针全绿才算数。

探针跟基准一样重要。下面所有性能数字都过了这关。

## 动手调优前的第一课：先查版本

第一次跑完我就吓了一跳：两张卡在 eager 模式下居然连 batch-invariant 自己的保证都没守住——prefill logprob 偏差约 0.02。撞上上游大 bug 了？差点以为是，结果是个**早就修掉**的真 bug。根因是一个 C++ RMSNorm kernel 的规约 block 大小会随 token 数变化，batch-invariant 拦截不到，上游几周前已经修了——只是我跑基准用的版本太旧，落在了修复之前。切到最新版本，eager 立马全绿。

学费很便宜，教训记一辈子：**基准不在最新版本上跑，结果就不算数。** 版本号从此进了我的检查清单，和 GPU 型号、驱动版本并列。

在新版本上重测，真正的吞吐税（编译模式）是：**4090D 上 29.9%，H20 上 35.0%**。延迟税更夸张：+73% 和 +110%。

## 找出税到底交在了哪

看代码时，batch-invariant 模块里有不少看起来很关键的按架构分支——比如给 Hopper 配的 cuBLAS workspace、给 sm8x 做的 aten 覆写。我没有凭代码猜，直接上了 profile。

profile 给出的画面简单得多：一开 batch-invariant，所有 cuBLASLt GEMM 全部消失，被同一个 Triton kernel `matmul_kernel_persistent` 顶掉了——因为 vLLM 的 linear 层把**所有架构**都直接导了进去。在一次 H20 的 profile 里，这一个 kernel 被调了 14,577 次，占掉 **79.4% 的 batch-invariant kernel 总耗时**，解释了大约 97% 的 kernel 耗时增量。我之前盯着看的那些按架构分支，在这条路径上全是死代码（顺手做了个 workspace 大小消融：改它对端到端耗时影响 ≤0.23%）。

单个 kernel、写死的 launch config、通吃所有架构和所有形状。这不叫交税，这叫留出来的调优空间。

## 让调优合法的唯一约束

对批不变 kernel 不能直接无脑 autotune——乱调配置恰恰是破坏不变性的最快办法。出路在于看清它**为什么**能保证不变：每个输出行的数值只取决于 **K 维规约顺序**。所以：

> **对于固定的权重形状 `(N, K)`，`BLOCK_K` 在所有 M 上必须保持恒定。**
> `BLOCK_M`、`BLOCK_N`、`num_warps`、`num_stages` 可以按 M 分桶自由变化——它们只影响调度，不改变规约顺序。

就这一条不变量，把能调的参数和绝对不能碰的参数彻底切开，也是这个 PR 的技术核心。每个候选配置依然要过逐位探针——推导要信，比特位更要验。

正确性测试还顺手带出个意外发现：在 4090D 的 K=2048 形状上，batch-invariant Triton kernel 过了 fp32 参考校验，反倒是 `torch.mm` 默认路径挂了——PyTorch 默认的 bf16 降精度规约累积了足够大的误差，精度上输给了“慢吞吞的确定性 kernel”。既确定，还更准。

## 19,200 个点的参数扫描

在两张卡上扫了 19,200 个配置点——M 分桶 × `BLOCK_M`/`BLOCK_N`/`num_warps`/`num_stages`，按形状锁死 `BLOCK_K`，每个配置过两道正确性门槛。结果如下：

| | decode GEMM（对比 torch） | prefill | 端到端吞吐税 |
|---|---|---|---|
| RTX 4090D | 0.25× → **0.77×** (3.0×) | 1.16× | 29.9% → **21.9%** |
| H20 | 0.21× → **0.59×** (2.8×) | 1.11× | 35.0% → **31.0%** |

延迟税掉得更狠：4090D 从 73% 降到 36%，H20 从 110% 降到 59%。

这个阶段有两个测量踩坑经历，换到任何项目都值得复述一遍：

- **不存在的 eager “性能退化”。** 调优后在 4090D 上测 eager 吞吐，第一眼居然慢了 44%。原因是按 M 分桶让 Triton JIT 编译次数暴涨（缓存条目从 3 变成 43），短基准把冷启动开销全吃进去了。热身后的稳态结果其实是 +1.2%。编译模式在图捕获阶段已经把这笔账预付了，所以当时没暴露出来。
- **幽灵 H20 数据。** 有一次 H20 的 eager 基线比其他所有轮次都慢了 ~40%。在编理由解释之前，我先查了机器身份——GPU UUID 和序列号显示，优化前后根本落在了**不同的物理机**上。重新在同一台节点上双边重跑并记下序列号，异常立刻消失，但我之前发出去的一个公开数字也因此不得不做了一次勘误。**优化前后必须证明在同一节点上，否则一律不算数。**

## 来自 `torch.compile` 的两次伏击

查表选配置的代码落在 `torch.compile` 会追踪的热路径上。两套看起来很“干净”的写法都在这儿阵亡了：

1. 给设备名查询套了 `functools.lru_cache` → Dynamo 直接穿过缓存追进了 pynvml 的 ctypes 调用 → 报 `Unsupported` → **编译模式下引擎直接起不来。** 算子单测和 eager pytest 全绿，只有真正跑一遍编译模式端到端才拦住了它，真发出去就是 P0 事故。
2. `bisect_left(..., key=...)` → 在当前版本 PyTorch 里同样报 `Unsupported`。

最终写法朴素得很：初始化时把设备解析成配置表存进模块级变量，查分桶直接在一个不超过 10 项的有序 tuple 上线性扫描。无聊、不怕追踪，速度还一样快。

验收清单再添一条：**只要代码可能被 Dynamo 追踪，测试计划里就必须包含一次真实的编译模式端到端运行，任何替代测试都不顶用。**

## PR Review 始末

我按具体设备名提了 PR，100 条配置项全部通过脚本跟扫描 JSON 做了机械交叉核对。维护者当天给出了第一条回复：

> "don't want to tune triton for older architecture, not used frequently in production"

担心很合理，但前提搞错了——H20 并不是老架构，它是当下的 Hopper，而且在大量真实生产集群里就是主力卡。我只回了一条事实澄清（没有多余争辩），并表示愿意收窄改动范围。维护者回复：“Ohh make sense for hopper — could you test e2e using vllm bench? Let's see if it's worth the complexity.”

于是决策标准落到了端到端数据上——完全照着维护者自己之前性能 PR 的格式来：贴出完整命令行、原始前后输出块、同节点测量纪律、上游整套确定性测试全过：

- **H20**：batch 8 延迟 −29.4%（1.42×），batch 32 延迟 −19.0%；吞吐 +3.4%
- **RTX 4090D**：batch 8 延迟 −23.0%，batch 32 延迟 −16.5%；吞吐 +12.0%

Review 意见直接反转：

> "Wow, very good perf improvement I didn't think about before, nice work"

又经过三轮 review（按维护者要求，把配置拆成独立文件，键名从具体卡名放宽到架构家族——`hopper` 由 H20 实测支撑，`ada` 由 4090D 支撑），PR 顺利合入。**从第一次测量到合入，一共七天。** 维护者计划在上面继续做后续调优和重构，架构家族的键位也顺带给 Blackwell 留好了带标签的空槽，等有卡的人直接填进来。

中间还有一个小插曲值得记一下：review 进行到一半，有另一位贡献者提出想把 H100 的配置顺手加进这个 PR——但数字是推算出来的，不是实测的。我请他先留到后续实测后再单独提 PR。调优 PR 全部的公信力都建立在**每个数字都有出处**之上；哪怕混进一行拍脑袋估算的数，整张表就废了。

## 能迁移到其他项目的经验

算子调优是写在简历上的那一行，真正能带走的是背后这套纪律：

1. **不在最新版本上跑，结果就不算数。** 我撞上最吓人的“bug”其实是个旧版本。
2. **先 profile，别轻信代码结构。** 那些按架构分支全是死代码，真正唱主角的只有一个占 79% 耗时的 kernel。
3. **找出让优化合法的不变量。** `BLOCK_K` 恒定这一条，把“确定性算子没法调优”变成了 19,200 个点的合法扫描。
4. **同节点、记序列号，做不到就重跑。** 一次跨节点测试让我欠了一次公开勘误。
5. **凡是可能被 Dynamo 追踪的代码，编译模式端到端测试是硬门槛。**
6. **在 review 里，一条事实澄清胜过长篇争辩**——按审稿人习惯的证据格式交作业，是拿到 approve 最快的路。
7. **每个数字都必须有出处**——你的表里如此，别人往你表里塞的也如此。
